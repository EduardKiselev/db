## Раздел 2. Данные и запросы

**Объясните модель данных в README.** Почему позиции встроены в заказ, а история покупателя хранится отдельными документами? Какой факт представляет цена в позиции заказа?

### Почему позиции встроены в заказ?

Заказ — атомарная единица учёта: его читают и пишут целиком, позиция без заказа не имеет смысла
и отдельно не запрашивается. Встраивание даёт атомарность одного документа (весь заказ создаётся
одной операцией), локальность (заказ со всеми позициями читается одним обращением).

### Почему история покупателя хранится отдельными документами?

История - это свершившийся факт, и цена на товар сегодня не должна влиять на данные истории, поэтому цены в истории не должны иметь отношения к products.

Хранение всей истории в документе с пользователем может быть избыточной из-за размера документа. Логичнее рядом с пользователем хранить только активные заявки и какие-то недавно завершенные заказы, а старые заказы хранить отдельно, это снизит размер документов пользователей.

### Какой факт представляет цена в позиции заказа?

Это исторический факт: цена единицы товара на момент покупки, поэтому ее нельзя брать из коллекции product

## Раздел 3. Отчёт о продажах

**Покажите в README расчёт количества и выручки одного товара** по позициям исходных заказов.

Расчёт выполняется целиком в aggregation pipeline:

1) `$match` отбирает `paid` и период `[from, to)`,
2) `$unwind` разворачивает позиции,
3) `$group` по `items.sku` объединяет размеры одного товара и считает `qty` и `revenue`
4) `$lookup` берёт названия из каталога,
5) `$sort` сортирует по выручке с вторичным ключом `sku` и делает порядок детерминированным при равной выручке,
6) `$limit` оставляет пять товаров.

Фактический результат совпал с эталоном по всем строкам и их порядку: A — 3 / 320.00,
B — 4 / 320.00, C — 3 / 270.00, D — 2 / 240.00, E — 1 / 200.00. У A и B равная выручка, порядок
определён вторичным ключом. Товар F (выручка 150.00) — шестой проданный, отсекается `$limit: 5`.

### Расчёт количества и выручки одного товара по позициям исходных заказов

Товар **A (Футболка)**, период `[2026-01-01T00:00:00Z, 2026-02-01T00:00:00Z)`:

| Заказ           | Дата             | Позиция |         qty | price  | qty × price     |
| -------------------- | -------------------- | -------------- | ----------: | ------ | ---------------- |
| `sale-start`       | 2026-01-01T00:00:00Z | `A / M`      |           2 | 100.00 | 200.00           |
| `sale-middle`      | 2026-01-15T12:00:00Z | `A / L`      |           1 | 120.00 | 120.00           |
| **Итого** |                      |                | **3** |        | **320.00** |

`qty = 2 + 1 = 3`; `revenue = 2×100.00 + 1×120.00 = 200.00 + 120.00 = 320.00`. Размеры `M` и `L`
объединены в одну строку группировкой по `items.sku`. Совпадает с эталоном.

Остальные заказы, содержащие товар A, в отчёт не вошли:

| Заказ                                     | Причина исключения                                           |
| ---------------------------------------------- | ----------------------------------------------------------------------------- |
| `excluded-end` (2026-02-01T00:00:00Z)        | верхняя граница периода исключается (`$lt`) |
| `excluded-before` (2025-12-31T23:59:59.999Z) | до начала периода                                              |
| `excluded-created`                           | `status: 'created'`, не `paid`                                          |
| `excluded-cancelled`                         | `status: 'cancelled'`, не `paid`                                        |

## Раздел 4. Индекс и план выполнения

**Объясните наблюдение.** Обоснуйте порядок полей индекса, опишите изменение работы запроса и одну
 издержку индекса. Если применяли `hint`, укажите это явно.

Создан составной индекс `{ userId: 1, status: 1, createdAt: -1, _id: 1 }`.

До опыта в коллекции `orders` из 10 000 документов был только стандартный индекс `_id_`. `hint` **не применялся** (`usesHistoryHint: false`) — планировщик
выбирает индекс самостоятельно.

### Таблица сравнения планов

| Вариант            | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
| ------------------------- | --------: | ----------------: | ----------------: | -------------------------------- |
| До индекса       |        20 |                 0 |            10 000 | да                             |
| После индекса |        20 |                20 |                20 | нет                           |

### Обоснование порядка полей индекса

Порядок следует правилу ESR. Сначала **Equality** — поля фильтра на равенство `userId` и `status`:
они задают непрерывный отрезок ключей, внутри которого лежат все подходящие документы.
Затем **Sort** — `createdAt: -1, _id: 1`, в том же порядке и с теми же направлениями, что и
сортировка запроса, поэтому обход индекса внутри этого отрезка уже выдаёт документы в нужном
порядке. **Range** в запросе нет, третий компонент пуст.

### Изменение работы запроса

До индекса планировщик выполнял полное сканирование коллекции (`COLLSCAN`, 10 000 документов)
и затем отдельную **блокирующую** стадию `SORT`: чтобы выбрать 20 самых свежих, нужно сначала
материализовать и сравнить все 1600 документов, подходящих под фильтр, — `SORT` не может выдать
ни одного результата, не потребив весь вход.

После создания индекса `IXSCAN` обходит ключи уже в нужном порядке, поэтому `LIMIT` проталкивается
внутрь сканирования и обход останавливается надвадцатом документе: стадия `SORT` исчезает, а
`totalDocsExamined` падает с 10 000 до 20.

### Издержки индекса

Индекс — отдельная структура, которую нужно поддерживать при каждой записи: любая вставка в
`orders` требует дополнительной записи в `history_user_status_date_id`, а обновление
индексируемого поля означает удаление старого ключа и вставку нового. Для активно пишущей
коллекции заказов это постоянная добавка к стоимости записи. То есть делать индексы стоит над
запросами, которые часто используются

## Раздел 5. Оформление заказа

**Объясните в README** различие атомарности и защиты от повторного бизнес-запроса, настройки транзакции и то, как ваш код приводит к commit или abort.

### Различие атомарности и защиты от повторного бизнес-запроса

Это ответы на два разных вопроса. **Атомарность** — «изменение в рамках одного выполнения
применилось целиком или нет?»: две записи в `products` и одна вставка в `orders` либо применяются
все, либо ни одной. **Защита от повтора** — «что будет, если один и тот же бизнес-запрос придёт
дважды?», и транзакция здесь не помогает: повторный вызов это новая корректная транзакция,
которая успешно закоммитится и спишет остатки второй раз. Повтор закрывается отдельно тем, что
`_id` заказа равен `operationId`, — второй документ с тем же `_id` создать физически невозможно,
а совпавший запрос возвращает уже сохранённый заказ. Третий случай, `REQUEST_CONFLICT` — тот же
`operationId` с другими параметрами: это не повтор доставки, а ошибка клиента, поэтому операция
отказывает вместо того, чтобы  вернуть прежний заказ.

### Настройки транзакции

`readConcern: 'snapshot'` даёт единый согласованный снимок на всю транзакцию, поэтому параллельные
закоммиченные записи не проявятся в середине, а чтение остатков и цены стабильно.
`writeConcern: {w: 'majority', j: true}` означает, что commit подтверждён большинством узлов и
зафиксирован в journal — заказ не потеряется при сбое primary. `readPreference: 'primary'`
обязателен, потому что многодокументные транзакции выполняются только на primary.

### Как код приводит к commit или abort

Команда при нормальном возврате делает`commitTransaction()`, а при исключении — `abortTransaction()` с последующим пробросом. Поэтому исход управляется  внутри `purchase`: `throw HWError('ITEM_UNAVAILABLE')`
или `throw HWError('REQUEST_CONFLICT')` приводят к abort, а `return order` (или `return existing`
при повторе) — к commit. В опыте с откатом `trace` зафиксировал первое успешное изменение внутри
транзакции (`sku: 'A'`, `matched: 1`, `modified: 1`) и последовавший неуспех второго
(`sku: 'B'`, `matched: 0`), то есть отказ произошёл после реальной записи, и откатывается именно она.

## Раздел 6. Смена primary

**Объясните в README**, как клиент находит новый primary и почему majority-подтверждение не гарантирует немедленно актуальное чтение с любой secondary.

### Как клиент находит новый primary

Узлы replica set обмениваются служебными сообщениями — heartbeats. По отсутствию связи
они обнаруживают недоступность primary. Это не позволяет мгновенно отличить остановку
процесса от задержки или разрыва сети: решение принимается по наблюдениям и тайм-аутам.
Если primary недоступен достаточно долго, secondary начинают выборы. После выборов и применения необходимых операций oplog, претендент переходит в primary. После этого драйвер при следующем опросе увидит, что появился новый primary.

### Почему majority-подтверждение не гарантирует немедленно актуальное чтение с любой secondary

`writeConcern: {w: 'majority', j: true}` гарантирует, что запись подтверждена большинством узлов
и зафиксирована в journal, то есть она долговечна и не будет откачена при смене primary. Но это
не гарантия, что запись уже видна на любой secondary: secondary применяют oplog асинхронно. Majority это большинство, но не все.

## Раздел 7. Шардирование

**Ответьте в README без развёртывания шардированного кластера. Коллекция `orders` распределена по ключу `{userId: 1}`; карта неизменна, на обоих шардах есть документы.**

| Диапазон userId                                                           | Шард    |
| --------------------------------------------------------------------------------- | ----------- |
| **Меньше 2000**                                                       | **A** |
| **От 2000 включительно до 5000 исключительно** | **B** |
| **От 5000 включительно**                                      | **A** |

1. **Какие шарды опросит `mongos` для истории `{userId: 2500}`, а какие — для общего отчёта по `{status: "paid"}`? Обоснуйте оба ответа.**
2. **Изменится ли число участников второго запроса после создания индекса `{status: 1}` внутри шардов? Какую работу этот индекс способен изменить?**

### Какие шарды опросит `mongos` для истории `{userId: 2500}`?

Только шард **B**. Запрос содержит ключ шардирования `userId` с условием на точное равенство,
а значение 2500 попадает ровно в один диапазон `[2000, 5000)`, закреплённый за B. По метаданным
о границах chunks из config server `mongos` выполняет targeted query и не обращается к A.

### Какие шарды опросит `mongos` для общего отчёта по `{status: "paid"}`?

Оба — **A и B**. В запросе нет условия на ключ шардирования: `status` не является ни ключом,
ни его префиксом, а предиката по `userId` нет вообще. Документы с `status: 'paid'` могут лежать
в любом диапазоне `userId`, поэтому отсечь шард невозможно.

### Изменится ли число участников второго запроса после создания индекса `{status: 1}` внутри шардов?

Нет, не изменится — запрос по-прежнему уйдёт на оба шарда. Маршрутизация определяется ключом
шардирования и границами chunks, о которых `mongos` знает из метаданных config server; индексы
внутри шардов — локальная деталь каждого шарда.

### Какую работу этот индекс способен изменить?

Он меняет стоимость выполнения **внутри каждого шарда**, но не состав участников и не объём
fan-out: на каждом шарде запрос `{status: 'paid'}` вместо `COLLSCAN` сможет использовать `IXSCAN`,
сократив `totalDocsExamined` и не просматривая заказы с другими статусами.
