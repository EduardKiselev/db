## Изменения окружения

Обе правки — в `docker-compose.yaml`, образ `mongo:8.0.30` сохранён без изменений
(требуется комплектом: `lab.js` отвергает любую другую версию).

1. **`bvfnname:` → `name:`.** Поле `bvfnname` не входит в схему Compose, из-за него
   `docker compose` отказывался даже валидировать файл:
   `additional properties 'bvfnname' not allowed`. `name: mongodb-homework` задаёт имя
   проекта — это согласуется с именами контейнеров `mongodb-homework-*`.

2. **`GLIBC_TUNABLES: glibc.pthread.rseq=1` на трёх узлах `m1`/`m2`/`m3`.**
   Хост работает на ядре Linux `7.0.0-38-generic`. MongoDB 8.0+ не стартует на ядрах 6.19+
   и завершается с сообщением `MongoDB cannot start: Linux kernel versions 6.19 and newer
   has a known incompatibility` (SERVER-121912).

   Причина: в ядре 6.19 изменилась подсистема **rseq** (restartable sequences), из-за чего
   ломается per-CPU кэш TCMalloc, используемый MongoDB 8.0+. Раньше `mongod` падал с
   segfault (exit 139), поэтому добавлена проверка версии ядра, завершающая процесс заранее.
   Переменная отключает проблемный rseq-путь, и проверка пропускается.

   Проверка версии не учитывает backported-уровень патчей Ubuntu (SERVER-136848): исправление
   на стороне ядра — в 7.0.14+, а нумерация Ubuntu `7.0.0-38` формально меньше, поэтому guard
   срабатывает даже на пропатченном ядре.

   Значение подобрано экспериментально: `rseq=1` запускает `mongod` штатно, `rseq=0` —
   немедленно упирается в guard.

Проверенные и **не работающие** обходные пути (для протокола): собственный `Dockerfile` на
`ubuntu:22.04` — контейнеры разделяют ядро хоста, `uname -r` внутри по-прежнему `7.0.0-38`;
`privileged: true`; `sysctls` (параметр не в отдельном kernel namespace).

### Замеченная особенность mongosh

`findOne(filter, options)` в `mongosh` трактует второй аргумент как **проекцию в legacy-форме**,
а не как объект опций драйвера:

| Вызов | Результат |
| --- | --- |
| `findOne({_id:"A"}, {projection:{price:1}})` | `{_id:'A'}` — цены нет, ключ `projection` воспринят как имя поля |
| `findOne({_id:"A"}, {price:1})` | `{_id:'A', price: Decimal128('100.00')}` |

В `purchase` использована вторая форма.

## Раздел 2. Данные, модель и запросы

### Валидатор `products`

Установлен через `collMod` с `$jsonSchema`, `validationLevel: 'strict'`, `validationAction: 'error'`.
Проверяются обязательные поля `_id`, `name`, `category`, `price`, `variants`; типы;
структура элементов `variants` (обязательные `size` и `stock`); неотрицательность цены и остатков.

Ключевые типы заданы явно, потому что именно тип отличает корректный документ от некорректного:
`price: {bsonType: 'decimal'}` и `stock: {bsonType: ['int','long'], minimum: 0}`.

Фактический результат проверки (сохранён в `results.json`, `validation`):

| Документ | Код | Причина |
| --- | ---: | --- |
| корректный | 0 | принят |
| `price: '100.00'` (строка) | 121 | отвергнут валидатором: тип не `decimal` |
| `variants: [{size:'L', stock: NumberInt(-1)}]` | 121 | отвергнут валидатором: `minimum: 0` |

Код 121 — `Document failed validation`, то есть причина отказа именно валидатор, а не
другое ограничение.

**Что валидатор сознательно не проверяет:** уникальность размеров внутри товара. В `$jsonSchema`
нет средства выразить «`size` не повторяется среди элементов массива» (`uniqueItems` сравнивает
элементы целиком, а не отдельное поле). Это ограничение обеспечивает приложение — иллюстрация
тезиса §3.3 о разделении ответственности между базой и приложением.

### Поиск товаров

Фильтр использует `$elemMatch`, а не два отдельных условия на массив:

```js
{ category: category,
  variants: { $elemMatch: { size: size, stock: { $gte: NumberInt(qty) } } } }
```

Без `$elemMatch` условия `{ 'variants.size': size, 'variants.stock': { $gte: qty } }`
проверялись бы **по разным элементам массива независимо**: товар подошёл бы, если размер L
есть в одном варианте, а остаток ≥ qty — в другом. `$elemMatch` требует, чтобы оба условия
выполнились для одного и того же варианта. Именно это проверяет контрпример задания: у товара A
`L` имеет остаток 0, а `M` — 10, поэтому поиск двух единиц `L` не возвращает A; после изменения
остатка `L` на 2 — возвращает.

Сортировка `{_id: 1}`, возврат полных документов со всеми вариантами, при отсутствии
совпадений — `[]`.

**Collation явно не задаётся.** Сравнение строк остаётся точным и чувствительным к регистру
(двоичное сравнение по умолчанию). Явная collation здесь была бы не просто избыточна, а вредна:
если collation запроса не совпадает с collation индекса, планировщик отказывается от обхода
индекса — и проверка `after uses IXSCAN without SORT` в разделе 4 провалилась бы.

Фактические результаты поиска:

| Вход | Ожидалось | Получено |
| --- | --- | --- |
| `clothes / L / 2` | `B, C` | `B, C` |
| `clothes / M / 5` | `A` | `A` |
| `accessories / L / 3` | `D` | `D` |
| `clothes / L / 99` | `[]` | `[]` |
| после `A/L = 2`: `clothes / L / 2` | `A, B, C` | `A, B, C` |

### История заказов

```js
c.orders.find({ userId: NumberInt(userId), status: status })
        .sort({ createdAt: -1, _id: 1 })
        .limit(20);
```

Возвращается курсор: один и тот же объект запроса используется и для получения результата,
и для `explain` в разделе 4.

Контрольный случай `{userId: 2500, status: 'paid'}` возвращает 20 документов
`H24, H25, H22, H23, …, H06, H07`. Порядок подтверждает обе части контракта сортировки:
пары `H24/H25`, `H22/H23` и т. д. имеют **одинаковый** `createdAt` (заказы генерируются по два
на час), и внутри пары порядок определяется вторым ключом — `_id` по возрастанию.
`H04, H05, H00…H03` отсекаются `limit(20)`.

Проверены также другой покупатель (`2501` → `other-user`), другой статус
(`cancelled` → `other-status`, `excluded-cancelled` — разные даты, поэтому порядок определяет
`createdAt`) и отсутствие совпадений (`9999` → `[]`).

### Модель данных

**Почему позиции встроены в заказ.** Заказ — атомарная единица учёта: его читают и пишут целиком,
позиция без заказа не имеет смысла и никогда не запрашивается отдельно. Встраивание даёт
(1) атомарность одного документа — весь заказ создаётся одной операцией, без транзакции;
(2) локальность — заказ со всеми позициями читается одним обращением;
(3) естественную границу размера — число позиций в реальном заказе мало, документ не растёт
неограниченно.

**Почему история покупателя — отдельные документы, а не массив в документе пользователя.**
История неограничена и растёт всё время. Массив в документе пользователя упёрся бы в лимит
16 МБ, а каждый новый заказ переписывал бы весь массив — растущая стоимость записи и конкуренция
за один документ. Отдельные документы позволяют эффективно индексировать и листать историю
(`limit 20`), а каждый заказ остаётся независимо адресуемым по `_id` — именно это используется
в разделе 5 для защиты от повтора.

**Какой факт представляет цена в позиции заказа.** Это **исторический факт**: цена единицы
товара на момент покупки, денормализованная в заказ. Она намеренно не выводится из каталога
при чтении — иначе изменение текущей цены задним числом переписало бы финансовую историю.
Это подтверждается двумя местами: отчёт в разделе 3 считает выручку по `items.price`,
а проверка `catalog price does not rewrite revenue` меняет цену A на `999.00` и требует
неизменности отчёта; в разделе 5 повтор покупки возвращает сохранённый заказ с исходными
ценами `100.00`/`80.00`, хотя цена A в каталоге к тому моменту изменена на `777.00`.

## Раздел 3. Отчёт о продажах

Топ-5 товаров по выручке за период `[from, to)` — начало включается, конец исключается;
учитываются только заказы со статусом `paid`.

```js
c.orders.aggregate([
  { $match: { status: 'paid', createdAt: { $gte: from, $lt: to } } },
  { $unwind: '$items' },
  { $group: { _id: '$items.sku',
              qty:     { $sum: '$items.qty' },
              revenue: { $sum: { $multiply: ['$items.qty', '$items.price'] } } } },
  { $lookup: { from: 'products', localField: '_id', foreignField: '_id', as: 'product' } },
  { $unwind: '$product' },
  { $project: { _id: 0, sku: '$_id', name: '$product.name', qty: 1, revenue: 1 } },
  { $sort: { revenue: -1, sku: 1 } },
  { $limit: 5 }
])
```

Расчёт выполняется целиком в aggregation pipeline MongoDB, не циклом в приложении.
`$group` по `items.sku` объединяет размеры одного товара; `$lookup` берёт названия из каталога;
`$sort` по выручке с вторичным ключом `sku` делает порядок детерминированным при равной выручке.

**Типы.** `items.qty` — int, `items.price` — Decimal128. `$multiply` повышает результат до
Decimal128, `$sum` сохраняет этот тип, поэтому `revenue` возвращается как Decimal128 с точной
шкалой (`320.00`, а не `320`).

### Расчёт количества и выручки одного товара по исходным заказам

Товар **A (Футболка)**, период `[2026-01-01T00:00:00Z, 2026-02-01T00:00:00Z)`:

| Заказ | Дата | Позиция | qty | price | qty × price |
| --- | --- | --- | ---: | --- | --- |
| `sale-start` | 2026-01-01T00:00:00Z | `A / M` | 2 | 100.00 | 200.00 |
| `sale-middle` | 2026-01-15T12:00:00Z | `A / L` | 1 | 120.00 | 120.00 |
| **Итого** | | | **3** | | **320.00** |

`qty = 2 + 1 = 3`; `revenue = 2×100.00 + 1×120.00 = 200.00 + 120.00 = 320.00`.
Размеры `M` и `L` объединены в одну строку группировкой по `items.sku`. Совпадает с эталоном.

**Почему остальные заказы с товаром A не вошли** (в каждом из них `A/M` с `qty: 999`, поэтому
любая ошибка фильтра немедленно завышает выручку на 99 900.00):

| Заказ | Причина исключения |
| --- | --- |
| `excluded-end` (2026-02-01T00:00:00Z) | верхняя граница периода исключается (`$lt`) |
| `excluded-before` (2025-12-31T23:59:59.999Z) | до начала периода |
| `excluded-created` | `status: 'created'`, не `paid` |
| `excluded-cancelled` | `status: 'cancelled'`, не `paid` |

Фактический результат совпал с эталоном по всем строкам и их порядку:

| sku | name | qty | revenue |
| --- | --- | ---: | --- |
| A | Футболка | 3 | 320.00 |
| B | Рубашка | 4 | 320.00 |
| C | Толстовка | 3 | 270.00 |
| D | Ремень | 2 | 240.00 |
| E | Сумка | 1 | 200.00 |

У A и B **равная выручка** 320.00 — порядок определяется вторичным ключом `sku` по возрастанию.
Товар F (Шарф, выручка 150.00) — шестой проданный товар, отсекается `$limit: 5`.
Таким образом, контрольный набор действительно проверяет и границу топ-5, и разрешение ничьей.

Дополнительно проверены: пустой период (2024) → `[]`; граница `from` включается
(`to = 2026-01-01T00:00:00.001Z` → только `sale-start` → `B 320.00`, `A 200.00`);
изменение текущей цены A на `999.00` не меняет отчёт.

## Раздел 4. Индекс и план выполнения

Исследован запрос истории на наборе из 10 000 заказов, параметры `userId: 2500`, `status: 'paid'`.
До опыта в коллекции только стандартный индекс `_id_` (проверяется сценарием).

Создан составной индекс `{ userId: 1, status: 1, createdAt: -1, _id: 1 }`
с именем `history_user_status_date_id`. `hint` **не применялся** (`usesHistoryHint: false`) —
планировщик выбирает индекс сам.

### Сравнение планов

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
| --- | ---: | ---: | ---: | --- |
| До индекса | 20 | 0 | 10 000 | да |
| После индекса | 20 | 20 | 20 | нет |

Стадии `winningPlan` из сохранённых полных планов (`explain-before`, `explain-after`):

- до индекса: `SORT` → `COLLSCAN`
- после индекса: `LIMIT` → `FETCH` → `IXSCAN`

Список `_id` и его порядок до и после создания индекса **идентичны** (проверки
`same IDs and order` и `matches independent fixture order`): индекс меняет способ доступа
к данным, но не результат запроса.

### Объяснение наблюдения

**Порядок полей — по правилу ESR (Equality, Sort, Range).**

1. **Equality** — поля из фильтра на равенство: `userId`, `status`. Они идут первыми, потому что
   задают непрерывный диапазон ключей индекса: все подходящие документы лежат в одном «отрезке»
   обхода, и ничего лишнего не просматривается.
2. **Sort** — поля сортировки `createdAt: -1, _id: 1` в том же порядке и с теми же направлениями,
   что и в запросе. Когда префикс равенства уже зафиксирован, обход индекса выдаёт документы
   сразу в нужном порядке.
3. **Range** — в этом запросе диапазонных условий нет, поэтому третий компонент пуст.

Направления важны: сортировка запроса `{createdAt: -1, _id: 1}` смешанная, поэтому индекс обязан
повторять её точно (`createdAt: -1, _id: 1`). Индекс с противоположными направлениями не подошёл бы
для обхода вперёд, хотя его можно было бы читать назад.

**Как изменилась работа запроса.** До индекса планировщик выполнял полное сканирование коллекции
(`COLLSCAN`, 10 000 документов) и затем **отдельную** стадию `SORT`: чтобы отсортировать по
`createdAt` и выбрать первые 20, нужно материализовать все подходящие документы и отсортировать их
в памяти (при нехватке памяти — с выходом на диск). `totalKeysExamined = 0`, потому что ключей
индекса не было вовсе.

После создания индекса `IXSCAN` обходит только 20 ключей, `FETCH` поднимает 20 документов,
а `LIMIT` завершает обход. Стадия `SORT` **исчезла** — порядок уже обеспечен индексом.
`totalDocsExamined` упал со 10 000 до 20, то есть в 500 раз; запрос перестал зависеть от
размера коллекции.

Отдельно стоит отметить соотношение `totalKeysExamined = totalDocsExamined = nReturned = 20`:
это признак точного попадания индекса — ни одного лишнего ключа или документа.

**Одна издержка индекса.** Индекс нужно поддерживать при каждой записи: любая вставка или
обновление `orders` требует дополнительной записи в индекс `history_user_status_date_id`,
причём обновление индексируемого поля означает удаление старого ключа и вставку нового.
Для активно пишущей коллекции заказов это постоянная добавка к стоимости записи
(write amplification). Дополнительно индекс занимает место на диске и в оперативной памяти —
составной индекс из четырёх полей на 10 000 документов конкурирует за кэш с самими данными,
вытесняя другие рабочие наборы.

## Раздел 5. Оформление заказа

Покупка списывает остатки двух разных товаров и создаёт один заказ в **одной**
многодокументной транзакции и **одной** сессии (оболочка `transaction()` из комплекта).

### Как код приводит к commit или abort

Оболочка `transaction(body)` начинает транзакцию, вызывает `body(c)` и далее:

- `body` **вернула значение нормально** → `commitTransaction()`;
- `body` **бросила исключение** → `abortTransaction()`, затем исключение пробрасывается дальше.

То есть исход полностью управляется потоком управления внутри `purchase`:

```js
throw HWError('ITEM_UNAVAILABLE', …)  // → abort
return order;                          // → commit
```

Порядок операций внутри `body`:

1. **Проверка повтора.** `c.orders.findOne({_id: operationId})`. Если заказ существует —
   сравниваются `userId` и каждая позиция по `sku`, `size`, `qty` **в порядке входа**.
   Совпало → вернуть сохранённый заказ (никаких записей). Не совпало →
   `throw HWError('REQUEST_CONFLICT')`.
2. **Списание остатков** — по одному `updateOne` на позицию. Проверка достаточности встроена
   **в условие обновления**, а не делается отдельным чтением:
   ```js
   { _id: item.sku, variants: { $elemMatch: { size: item.size, stock: { $gte: qty } } } }
   { $inc: { 'variants.$.stock': NumberInt(-item.qty) } }
   ```
   `matchedCount === 0` означает, что нет товара, размера или достаточного остатка →
   `ITEM_UNAVAILABLE`. Такой подход исключает гонку «прочитали остаток, затем списали»:
   условие и изменение применяются одной атомарной операцией.
   После каждой попытки вызывается `trace({event:'update_inside_transaction', sku, matched, modified})`.
3. **Чтение цены** позиции из каталога внутри той же транзакции.
4. **Создание заказа** — один `insertOne` с `_id = operationId`, `userId`, `createdAt = new Date()`,
   `status = 'created'`, позициями в порядке входа и ценами покупки.

### Типы: ловушка с `$inc` и валидатором

`$inc` обязан получать `NumberInt(-item.qty)`, а не JS-число. `$inc` с double-значением
превращает int32-поле в double, а сценарий `purchase` заранее устанавливает на `products`
строгий валидатор с `stock: {bsonType: ['int','long']}` и `validationLevel: 'strict'`.
Обновление, которое сделало бы остаток дробным типом, было бы отвергнуто с кодом 121 —
и покупка падала бы по неочевидной причине. По той же схеме `userId` и `items[].qty`
сохраняются через `NumberInt`, а `items[].price` остаётся Decimal128 из каталога.
Проверка `stored BSON types: integer user/qty, decimal prices, date` это подтверждает.

### Атомарность и защита от повторного бизнес-запроса — разные вещи

**Атомарность** отвечает на вопрос *«изменение применилось целиком или нет?»* в рамках
**одного** выполнения. Две записи в `products` и одна вставка в `orders` — три документа;
транзакция гарантирует, что либо применятся все три, либо ни одного. Это демонстрирует опыт
с откатом: первое списание (`A/M`) реально проходит внутри транзакции, второе (`B/L`, qty 6
при остатке 5) не находит документ, и `abort` возвращает **оба** остатка к исходным значениям,
а заказ не появляется.

**Защита от повтора** отвечает на другой вопрос: *«что будет, если один и тот же бизнес-запрос
придёт дважды?»* Транзакция здесь **не помогает**: повторный вызов — это новая корректная
транзакция, которая успешно закоммитится и спишет остатки второй раз. Защита строится
отдельно, на идентичности запроса: `_id` заказа равен `operationId`, поэтому второй документ
с тем же `_id` создать физически невозможно, а совпавший запрос возвращает уже сохранённый заказ.

Отсюда и третье состояние — `REQUEST_CONFLICT`: тот же `operationId` с другими параметрами.
Это не повтор доставки, а ошибка клиента (или злоупотребление), поэтому операция отказывает
вместо того, чтобы молча вернуть прежний заказ.

Сравнение при повторе идёт по **значениям** `userId`, `sku`, `size`, `qty` в порядке входа,
а не по тексту JSON и не по текущей цене каталога. Сценарий проверяет это напрямую: между
успешной покупкой и повтором цена A меняется на `777.00`, а ключи в объектах запроса
переставлены — повтор всё равно recognised как тот же запрос и возвращает исходный заказ
с ценами `100.00`/`80.00` без единой записи.

### Настройки транзакции

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `readConcern` | `snapshot` | единый согласованный снимок на всю транзакцию: параллельные закоммиченные записи не «проявятся» в середине, чтение остатков и цены стабильно |
| `writeConcern` | `{w: 'majority', j: true}` | commit подтверждён большинством узлов и записан в journal — заказ не потеряется при сбое primary |
| `readPreference` | `primary` | многодокументные транзакции выполняются только на primary |

### Счётчики транзакций

Снимки `serverStatus().transactions` сняты вне транзакционной сессии, с одного primary
и одного процесса (`sameProcess: true` в обоих опытах); между снимками другие транзакции,
перезапуски и смена primary не выполнялись.

| Опыт | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
| --- | ---: | ---: | ---: |
| Новая успешная покупка | 1 | 1 | 0 |
| Откат после первого списания | 1 | 0 | 1 |

Значения совпали с ожидаемыми **+1/+1/0** и **+1/0/1** точно, без отклонений: драйвер
не повторял попытки, поэтому объяснять расхождение счётчиков не требуется.
Для повтора завершённой покупки (`replay`) нулевая разность не требуется — повтор
обрабатывается чтением существующего заказа до начала списаний.

Счётчики подтверждают, что сервер действительно увидел старт и commit/abort транзакции,
но они общие для процесса и сами по себе не доказывают атомарность: доказательство дают
состояния данных (оба остатка восстановлены, заказа нет).

### Фактические результаты опытов

| Случай | Результат | Изменения в базе |
| --- | --- | --- |
| Новая успешная покупка | `Order` `_id = 'purchase-001'`, `status = 'created'`, цены `100.00`/`80.00` | `A/M 10→8`, `B/L 5→4`, один заказ |
| Повтор подтверждённой покупки | тот же сохранённый `Order` | записей нет |
| Нехватка второго товара (`B/L`, qty 6) | `ITEM_UNAVAILABLE` | все изменения отменены, заказа нет |
| Прежний `operationId`, `qty` 2→3 | `REQUEST_CONFLICT` | данных не изменено |
| Отсутствующий размер `B/XXL` | `ITEM_UNAVAILABLE` | откат |
| Неизвестный SKU `NO_SUCH_SKU` | `ITEM_UNAVAILABLE` | откат |

В опыте с откатом `trace` зафиксировал первое успешное изменение внутри транзакции
(`sku: 'A'`, `matched: 1`, `modified: 1`) — то есть отказ произошёл **после** реальной записи,
а не до неё, и откатывается именно она.

## Раздел 6. Смена primary

Опыт выполнен на том же replica set, база `hw2_failover`, **один и тот же экземпляр клиента**
на все операции (проверка `same client instance` сравнивает `client === db.getMongo()`).

| Шаг | Результат |
| --- | --- |
| Роли до | `m1: SECONDARY`, `m2: SECONDARY`, `m3: PRIMARY` |
| Запись `before` с `{w:'majority', j:true}` | `acknowledged: true` |
| `replSetStepDown` (60 с, `secondaryCatchUpPeriodSecs: 10`) | primary сменился |
| Чтение документа `before` тем же клиентом | `message: 'majority confirmed before stepDown'` |
| Запись `after` тем же клиентом | `acknowledged: true` |
| Роли после | `m1: PRIMARY`, `m2: SECONDARY`, `m3: SECONDARY` |
| Документов в `probe` | 2 |

`writeProbe` реализован как `updateOne` с `upsert: true` и `$set`, поэтому повтор вызова
с тем же `id` безопасен: оболочка опыта может повторить запись после потери ответа при
переключении, и это не создаст второй документ и не изменит уже подтверждённое сообщение.

### Как клиент находит новый primary

Адрес подключения **не менялся вручную**: строка соединения — это seed list
`mongodb://m1:27017,m2:27017,m3:27017/?replicaSet=hw2rs`, то есть список кандидатов и имя
replica set, а не адрес конкретного узла.

Драйвер ведёт фоновый мониторинг топологии: периодически опрашивает узлы из seed list
командами `hello`/`isMaster` и по ответам строит карту — кто primary, кто secondary,
какой у набора конфигурационный термин. Когда `m3` выполняет `stepDown`, он перестаёт
отвечать как primary; драйвер обнаруживает это и запускает повторное определение топологии,
находя узел, который теперь сообщает `isWritablePrimary: true` (в нашем опыте — `m1`).
Запросы прозрачно перенаправляются на него.

Приложение при этом не пересоздаёт клиент и не подменяет адрес: seed list содержит все три
узла, поэтому для перенацеливания достаточно уже имеющейся информации. Кратковременные
ошибки в окне выборов (пока нового primary ещё нет) допустимо обработать повтором после
готовности primary — оболочка сценария так и делает, а `retryWrites=true` в URI покрывает
часть повторов на уровне драйвера. Сохранять одно физическое соединение не требуется:
идентичность клиента определяется экземпляром объекта, а не TCP-соединением.

### Почему majority-подтверждение не гарантирует немедленно актуальное чтение с любой secondary

`writeConcern: {w: 'majority', j: true}` означает: запись **подтверждена большинством** узлов
набора и **зафиксирована в journal** на primary. Это гарантия durability и защиты от отката —
такая запись переживёт смену primary и не исчезнет.

Но это **не** гарантия, что запись уже видна на любой secondary. Secondary применяют oplog
**асинхронно**, собственными потоками, и подтверждение majority считается по факту получения
записи узлами, а не по факту её применения и открытия для чтения. Поэтому в любой момент
времени часть secondary может отставать (replication lag) и не содержать только что
подтверждённую запись.

Следствие: чтение с произвольной secondary сразу после majority-записи может вернуть устаревшие
данные. Запись при этом не потеряна — она просто ещё не видна в этой точке.

Чтобы прочитать собственную запись, нужно явно задать условие:

- `readPreference: 'primary'` — читать только с primary (так настроен стенд);
- causal consistency в рамках сессии — драйвер передаёт время операции и secondary отвечает
  лишь после применения oplog до этого момента (`afterClusterTime`);
- read concern уровня `majority`/`linearizable` для соответствующих гарантий.

В нашем опыте чтение документа `before` после переключения выполняется при `readPreference: primary`
с нового primary, поэтому оно возвращает подтверждённый документ — что и фиксирует проверка
`old majority document read`.

## Раздел 7. Шардирование

Кластер не развёртывался; ответы по заданной карте chunks. Коллекция `orders`
распределена по ключу `{userId: 1}`:

| Диапазон `userId` | Шард |
| --- | --- |
| < 2000 | A |
| [2000, 5000) | B |
| ≥ 5000 | A |

### Вопрос 1. Какие шарды опросит `mongos`

**История `{userId: 2500, status: 'paid'}` — только шард B.**

Запрос содержит **ключ шардирования** `userId` с условием на точное равенство. Значение 2500
попадает ровно в один диапазон `[2000, 5000)`, который закреплён за шардом B. `mongos`
выполняет **targeted query**: по метаданным о границах chunks из config server он определяет,
что ни один chunk на шарде A не может содержать документ с `userId = 2500`, и отправляет запрос
только в B. Поле `status` в маршрутизации не участвует — оно не входит в ключ шардирования.

**Общий отчёт по `{status: 'paid'}` — оба шарда, A и B.**

В запросе **нет** условия на ключ шардирования: `status` не является ни ключом, ни его префиксом,
а предиката по `userId` нет вообще. Документы с `status: 'paid'` могут лежать в любом диапазоне
`userId`, поэтому `mongos` не может отсечь ни один шард и выполняет **scatter-gather**:
рассылает запрос всем шардам, а затем объединяет и сортирует их ответы.

Практическое следствие для отчёта из раздела 3: агрегация по всему периоду будет выполняться
частично на каждом шарде, а `mongos` отвечает за слияние — в том числе за корректность
`$sort`/`$limit` поверх объединённых данных.

### Вопрос 2. Изменится ли число участников после создания индекса `{status: 1}` внутри шардов

**Нет, не изменится: запрос по-прежнему уйдёт на оба шарда.**

Маршрутизация определяется **ключом шардирования и границами chunks**, о которых знает `mongos`
из метаданных config server. Индексы внутри шардов — локальная деталь каждого шарда; `mongos`
не использует их для решения о том, куда отправить запрос, и в его карте chunks ничего
не появляется от создания shard-local индекса. Поскольку предиката по `userId` в запросе всё
ещё нет, отсечь шарды по-прежнему невозможно.

**Какую работу этот индекс способен изменить.** Он меняет **стоимость выполнения внутри каждого
шарда**, но не состав участников и не объём fan-out. На каждом шарде запрос
`{status: 'paid'}` вместо полного сканирования коллекции (`COLLSCAN`) сможет использовать
`IXSCAN` по индексу `{status: 1}`, сократив `totalDocsExamined` и избавившись от просмотра
заказов с другими статусами. То есть индекс уменьшает работу на узле, но не уменьшает число
узлов, к которым нужно обратиться.

Отсюда общий принцип: чтобы сократить **маршрутизацию**, индекс нужно строить так, чтобы запрос
содержал условие на ключ шардирования (или его префикс) — например, добавить в запрос диапазон
`userId`. Индекс на неключевом поле даёт выигрыш в execution, но не в routing.

Стоит также учесть издержку: индекс `{status: 1}` имеет низкую селективность (всего три
возможных значения — `created`, `paid`, `cancelled`), поэтому при большом числе `paid`-заказов
выигрыш может оказаться незначительным, тогда как стоимость поддержки индекса при каждой записи
остаётся постоянной.
